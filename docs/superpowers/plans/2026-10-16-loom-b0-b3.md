# Loom B0–B3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Landing fixes, `loom init` in every repo state, TS/Go language support with compiler gates, and the lead: one Claude session you can chat with from both the terminal and the dashboard, plus plan files and the plan checker.

**Architecture:**
- The daemon stays the hub.
- The lead is the user's own `claude`, started with `--dangerously-load-development-channels server:loom`.
- `loom-mcp` doubles as the channel. It opens a localhost port, registers it with the daemon, and turns daemon pushes into `notifications/claude/channel` events.
- Hooks mirror the conversation into `turn` and `tool` events and onto an SSE stream.
- Plans are Markdown files with YAML front matter under `.loom/plans/`. One pure checker serves the CLI, the route and the MCP tool.

**Tech Stack:**
- TypeScript (node 22, tsx, esbuild for the hook and mcp bundles), vitest, FalkorDB.
- `@modelcontextprotocol/sdk` 1.32.1.
- `yaml` 2.9.1.
- Claude Code 2.1.301.

**Spec:** `docs/superpowers/specs/2026-10-16-loom-product-design.md` (§3.1–§3.3, §4, §6, §8 B0–B3, §11).

## Global Constraints

- Claude Code runs on the subscription only. Every spawn strips `ANTHROPIC_*`. Proofs also strip `CLAUDE*` so the session behaves like a user's terminal.
- TDD: RED, then GREEN. Never tune a test to pass. Proofs use real `claude`, real git and the real CLI. Nothing in Loom is mocked.
- Each step (B0, B1, B2, B3) gets its own branch, stacked: `feat/b0-base` → `feat/b1-init` → `feat/b2-langs` → `feat/b3-lead`. Each gets a PR into its parent, and the user merges.
- Commit footer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Leave untracked `bench/results/t4.*` and `packages/indexer/smoke/` alone.
- The daemon UI runs on port 4327 (`LOOM_UI_PORT=4327`).
- Never mention Django in the UI.
- `turn.text` is capped at 4000 chars (`cut:true` when cut) and redacted before it is written.
- The channel server name is `loom`, so the flag value is `server:loom`.
- Token: `~/.loom/token`, created by the daemon (mode 0600). New routes require header `x-loom-token` or query `token`. Existing routes keep working unchanged.

## Spike results (B3 pre-check, run 2026-10-16 on 2.1.301)

Evidence is in `docs/proofs/b3-spike.md`, written in Task 12.

1. **Channel input works.** The server declares `experimental['claude/channel']`. A `notifications/claude/channel` event reaches the session, and the `UserPromptSubmit` hook receives it with `prompt = <channel source="loom" from="dashboard">\n…\n</channel>`.
2. **A message sent mid-turn is folded into the running turn.** It is injected at the next tool boundary, and the model may not answer it separately. So the daemon holds dashboard messages while the session is busy (from `UserPromptSubmit` until `Stop`) and releases one per `Stop`.
3. **The permission relay works.**
   - `permission_request {request_id, tool_name, description, input_preview}` arrives at the server.
   - Answering with `notifications/claude/channel/permission {request_id, behavior:'allow'}` runs the tool.
4. **The dev-channel confirmation shows on every launch, not just once.** `loom lead` says so before it starts Claude.
5. **Process tree:** the MCP server's `ppid` is the `claude` pid.

## Review Focus

1. **Daemon down while the lead runs.** Hooks fail open, `loom-mcp` keeps serving tools, and the channel re-registers when the daemon returns. Test: in Task 15, channel registration retries.
2. **Two lead sessions in one repo** (two terminals). Each has its own per-sid active file and its own channel. A message goes only to the sid it was posted to. Test in Task 13 and Task 15.
3. **Secrets in prompts.** `sk-ant-…`, `ghp_…`, AWS keys and `.env` values never reach `.loom/sessions`. Test in Task 14.
4. **An `init` re-run on a repo already set up** changes nothing tracked. Test in Task 7.
5. **A malformed plan file** (bad YAML, a non-list `tasks`) gives problems, not a crash: a 200 response with `ok:false`. Test in Task 17.

- On start it listens on `127.0.0.1:0` with a random 32-hex `secret`, then POSTs `/channels {pid: process.ppid, port, secret, cwd}` to the daemon. It retries every 5 s until accepted, and re-registers on daemon restart (it notices a 404 from the daemon on a push-health ping every 15 s).
- Push server: `POST /push {secret, content, meta}` and `POST /permission {secret, request_id, behavior}`. A wrong secret → 403.
- It forwards `notifications/claude/channel/permission_request` to the daemon at `POST /channels/permission {pid, ...params}`.
- `class Channels`:
  - `register({pid, port, secret, cwd})`
  - `bind(claudeSid, ppids: number[])`: on SessionStart, matches any registered pid.
  - `send(sid, text): 'sent'|'held'|'no-channel'`
  - `onStop(sid)`: flushes one held message.
  - `answer(sid, rid, behavior)`
  - `pending(sid)`
- `POST /sessions/:sid/messages {text}` (token) → `{status}`. `held` when busy. `no-channel` → 409, with `read-only: restart the lead with loom lead to chat here`.
- `permission` bus events carry `{rid, tool, description, preview}`. The first answer wins: an answer to an unknown or answered rid → 409.
